## 展示目標

一條可以重複演示的路徑（毛研食品，帳號 `yu`）。全程都在同一個專案的「文件」頁進行，AI 助手開在側邊；跨出「文件／資料」頁時，AI 助手會照既有規則重建並清空對話（`App.tsx` 的 `previewKey`），這次不改：

1. 在專案的「文件」上傳一份文件，例如「G2 關卡檢查表.txt」。文件列上出現「AI：排隊中」，約 10～20 秒內變成「AI：可查詢」，不用按任何鈕。
2. 打開 AI 助手，點「正式文件」，問「G2 要具備什麼才能通過？」。回答附來源。
3. 接著問「那需要誰簽核？」。問題下方顯示「已理解為：G2 需要誰簽核？」，回答仍引用 G2 文件。
4. 點來源，看到原文段落、文件第幾版、所屬專案／節點、頁或段，可以按「下載原檔」。
5. 對回答按「有幫助」。
6. 點開這份文件的明細，按「停用 AI 引用」（文件列上的標籤變成「AI：已停用」）。再問一次，AI 不再引用它；剛才那則回答的來源仍可開啟。
7. 按「新對話」清空對話，再問的問題不會被當成追問。

## 五項功能

### 1. 連續追問

- **適用範圍**：文件問答、新人報到、正式文件三個分類（都是 `mode: 'rag'`）。資料分析（SQL）不帶歷史。
- **前端**：
  - 同一分類的對話裡，前面已完成的問題，以使用者原本輸入的文字送出 `history`。最多 6 題、合計最多 6000 字，從最新的往回算。
  - 失敗的題目不送。只送問題，不送回答。
  - 以下情況會清空對話，下一題不帶歷史：
    - 按新增的「新對話」鈕
    - 切換分類
    - 重新整理、登出、切換公司或帳號（沿用目前元件重建的行為）
  - 關閉再打開面板時，對話保留。
- **API**：
  - `Ask` 新增 `history: list[str]`。每題 1～2000 字，最多 6 題，合計最多 6000 字，超過回 422。
  - 只允許 `mode == 'rag'`，其他模式帶非空歷史回 422。
  - 回應新增 `standalone_question`（實際拿去查詢的問題）和 `followup`，`followup` 的值是 `none`、`model`、`combined` 或 `clarification` 其中之一。
- **新模組 `api/app/ai/followup.py`**，判斷順序如下：
  1. 沒有歷史 → 原題照查，`followup='none'`。
  2. 問題不像追問 → 原題照查。像追問的規則參考 RAG-V1 `conversation.py` 的 `REFERENTIAL` 和省略句規則：
     - 以「那／那個／這個／這項／上述／前述／它／他們」開頭，而且後面不是「專案」
     - 整句只有「誰簽核／核准／追蹤」「還缺哪些（文件）」「接著呢」「然後呢」「怎麼辦」這類短句
  3. 公司已啟用本地模型 → 用 `model.chat()` 改寫：
     - 參數：溫度 0、輸出上限 500 tokens、逾時 15 秒。
     - 輸出 schema：`{standalone_question, needs_clarification}`。
     - 系統提示：只補上被省略的主詞；優先用最近一題的主詞；只有真的找不到主詞時才要求補充。
     - 只送使用者自己的問題文字，不送文件內容或來源標題。
     - 結果為 `needs_clarification`：回 `kind='clarification'`，答案是固定文字「請補充您指的是哪個專案、階段或文件，以及要查詢的事項。」，不做檢索，`followup='clarification'`。
     - 解析失敗或逾時：改走第 4 點。
  4. 沒有模型或改寫失敗 → 把「最近一題＋這一題」接成查詢句，`followup='combined'`。介面顯示「已合併上一題一起查詢」。
- **改寫後怎麼用**：檢索與回答都用 `standalone_question`，後面流程（權限、分級、閘道、引用驗證、拒答）完全不變。
- **稽核**：`ai.query` 的 payload 加 `followup`，不記問題文字（維持現狀）。

### 2. 上傳後自動建索引（含 15173 這類 PostgreSQL 部署）

- **沿用 main 的做法**：
  - 正式文件索引仍是 `PF_AI_ROOT/formal-v1/` 下的衍生 SQLite 檔，用 `refresh(only_if_changed=True)` 做增量更新。
  - 背景由 `index_worker` 每 10 秒檢查一次，掃描可見來源的 metadata，有變動才處理。
  - **不搬** RAG-V1 的 `rag_indexes` 排隊資料表。
- **開放到 PostgreSQL**：
  - `formal_index.enabled()` 改成只看 `PF_AI_FORMAL_INDEX=true`，不再要求 `PF_ACCEPTANCE_MODE`。
  - 拿掉索引相關路徑對 `sqlite` 的限制：`/ai/ask`、`/ai/documents`、`/ai/index/*`、`/ai/status` 的 `formal_available`、`index_worker.tick/running`，以及新的 `/ai/knowledge`。
  - **AI 治理頁不開放**：`governance_admin()` 目前也用 `require_enabled()`。要把它拆成兩個檢查，讓 `/ai/governance`、`/ai/classification`、`/ai/policy`、`/ai/mask-preview` 維持原本「驗收模式＋SQLite」的限制；15173 的「AI 政策與稽核」照舊是示例頁。
  - 自動更新仍另需 `PF_AI_INDEX_AUTO_UPDATE=true`。
  - `deploy/docker-compose.yml` 的 api 服務帶入這兩個變數，預設 `false`；`deploy/.env.example` 加說明。
  - API 容器維持單一 uvicorn 程序（現狀）。文件註明不支援多程序。
- **觸發時機**：不另加上傳鉤子，靠 10 秒輪詢。上傳、新版本、網頁文字編輯、樣板產生、收件匣匯入，都會在下一輪被偵測到。
- **失敗處理**：
  - 格式不支援、超過 10MB、檔案損毀這類固定失敗，照現狀標 `skipped` 並保留原因；來源改版後自動重做。
  - 暫時性 I/O 錯誤，照現狀保留舊索引，下一輪重試。
  - 不另做單檔重試鈕。
- **既有文件**：第一次啟用時，增量更新會把所有可見文件建進索引。每家公司上限 500 個來源版本，照現狀。
- **文件列狀態**：
  - 新增 `GET /ai/knowledge?node_id=…` 或 `?project_id=…`（擇一，不可同時給），讀取權限同文件清單。
  - 回傳該範圍每份文件的 `{document_id, ai_enabled, state, reason, indexed_version}`。`state` 的值為：
    - `indexed`：可查詢
    - `pending`：排隊中
    - `skipped`：無法索引，附原因
    - `disabled`：已停用
  - 正式索引未啟用時回 404，前端不顯示 AI 欄。
  - 前端在有 `pending` 時每 5 秒重查，其他時候不輪詢。

### 3. 停用／恢復文件知識

- **資料**：`documents` 加 `ai_enabled`（boolean，非空，`server_default=true`），放在 migration `20261102_0024`。存在文件層，所以改版不會改變它。
- **API**：
  - `PUT /ai/knowledge/{document_id}`，body `{enabled: bool}`，多餘欄位回 422。
  - 權限沿用 `document_store.permission(..., write=True)`：節點文件要 `can_write_record`，專案文件要 `can_manage_project`。沒有權限回 403，跨公司或看不到回 404。
  - 稽核寫 `log_audit(db, current, 'ai.knowledge', node_id, {document_id, enabled})`。
- **效果**（照 RAG-V1 的做法：保留段落，只是不拿來回答）：
  - 索引更新（`refresh`）照樣處理已停用的文件，段落留在索引裡。
  - 查詢（`/ai/ask` 的檢索）和文件列狀態排除 `ai_enabled=false` 的文件，所以停用後下一題立刻不會引用它。
  - 恢復後立刻可以再被引用，不用重新排隊。
  - 開啟舊來源（`formal_index.document`）不看 `ai_enabled`，也允許歷史版本（標示「歷史版本」），每次照舊重查讀取權和 SHA-256。所以文件停用後、或上傳新版本後，先前回答的來源都還能開啟和下載。
  - 附件不在這次範圍內。
- **前端**：在文件管理的每份文件旁顯示 AI 狀態標籤，有 `can_write` 的人另外看到「停用 AI 引用／恢復 AI 引用」鈕。

### 4. 回答回饋

- **資料**：同一個 migration 新增 `ai_answers` 表：
  - 欄位：`id`（uuid 字串）、`organization_id`、`user_id`、`dataset`、`mode`、`kind`、`followup`、`source_ids`（JSON，chunk id 清單）、`rating`（可空，CHECK 只能是 `helpful`／`unhelpful`）、`created_at`。
  - 外鍵連到公司與使用者。
  - **不存問題、答案和文件全文**，與 RAG-V1 相同。
- **寫入**：
  - `/ai/ask` 成功時，在寫 `ai.query` 稽核的同一個交易裡新增一列，回應帶 `answer_id`。
  - `/ai/preview`、錯誤、`kind='clarification'` 不寫。
- **API**：
  - `PUT /ai/answers/{answer_id}/feedback`，body `{rating}`。只有提問者本人可以評（同公司且同使用者，否則 404），可以改評。稽核寫 `ai.feedback`，內容是 `{answer_id, rating}`。
  - `GET /ai/feedback/summary`：限公司管理者（`role=='admin'`），其他人 403。回傳近 30 天的 `{helpful, unhelpful, total_answers}`。
- **前端**：
  - 有 `answer_id` 的回答下方顯示「有幫助」「沒有幫助」兩個小鈕，按下後顯示「已記錄：有幫助」。
  - 管理者在 ⚙ 進階區看到一行「回饋（近30天）：有幫助 N／沒有幫助 M／回答 T」。

### 5. 點引用看原文

- **來源欄位**：正式文件來源（`formal-v1`）在現有欄位外新增以下欄位。不改既有欄位名稱。
  - `document_ref`：`{kind:'document', document_id, version}` 或 `{kind:'attachment', attachment_id}`
  - `project_title`
  - `node_title`（專案層級文件為 null）
  - `page`（從段落內「第N頁」標頭取得，沒有就 null）
- **開啟原文**：`GET /ai/documents/{chunk_id}` 照現狀，每次重查權限和 SHA-256，回應補上述欄位。
- **檢視器內容**：標題、第幾版（現行／歷史）、專案／節點、頁或段、原文段落（`<pre>`，不用 innerHTML），以及「下載原檔」鈕：
  - 文件走既有的 `/documents/{id}/versions/{v}/download`
  - 附件走既有的 `/attachments/{id}/download`
  - 這兩個端點本來就會自己檢查權限。
- **權限失效**：開啟或下載回 401 時沿用現有的 `expired()`；回 403 或 404 時，只在這個來源顯示「你目前無法查看這個來源」，不清掉整段對話。
- **不搬**：RAG-V1 每 30 秒重驗舊回答（`/rag/queries/revalidate`）。因為每次開啟和下載都會重查權限，這次不需要。
- 文件問答、新人報到這兩個 AI 展示資料集的來源維持現狀，沒有下載。

### 「正式文件」分類

- 只要 `/ai/status` 的 `formal_available` 為真就顯示，六家公司都會有。
- 固定快捷題仍只有毛研食品有，其他公司只顯示輸入框。

## 驗收情境

- 上一節「展示目標」的 7 步，在隔離預覽與（部署後的）15173 都能走完，1280 和 375 都沒有水平捲動或遮擋。
- **沒有啟用模型時**：
  - 追問顯示「已合併上一題一起查詢」，來源仍是 G2 文件。
  - 回答是檢索原文，照現狀。
- **權限**：
  - 毛研食品的一般成員（例如 `ming`），對沒有寫入權的文件看不到停用鈕。
  - 他公司帳號看不到這些文件，也不會被引用。
  - 他人的 `answer_id` 不能評分。
- **停用後**：新問題不引用該文件；先前回答的來源仍可開啟和下載；上傳新版本後仍是停用。
- **管理者**：⚙ 看得到回饋統計，非管理者看不到。

## AI 代決（展示模式，交使用者核對）

1. 第一次啟用時，**既有文件全部建進索引**。這和先前討論時「舊文件要手動重試」的猜測不同，理由是資料量小，而且有 500 的上限。
2. 不搬 RAG-V1 的排隊表，沿用 main 每 10 秒的增量檢查。固定失敗會顯示原因，改版後重做；暫時性錯誤下一輪自動重試。不做單檔重試鈕。
3. 沒有模型時，追問改用「上一題＋這一題」一起查，不像 RAG-V1 那樣要求補充。
4. `ai_answers` 不存問題、答案和文件全文。
5. 「正式文件」分類開放給六家公司，快捷題仍只有毛研食品有。
6. 停用只做文件，不做附件；已停用文件的舊引用仍可開啟。
7. 正式索引不再要求驗收模式，改由 `PF_AI_FORMAL_INDEX` 單獨控制，預設關閉。
8. 15173 的部署要等使用者同意後才做。
9. 停用文件時保留索引段落，只在查詢時排除（同 RAG-V1）。舊來源在文件停用或改版後都還能開啟（允許歷史版本，重查權限）。
10. AI 治理頁（政策、分級、遮罩預覽）維持只在隔離驗收環境開放，不跟著開到 PostgreSQL。
11. 不改「跨出文件／資料頁就清空 AI 對話」的既有規則，展示路徑全程留在文件頁。
12. 展示時使用這台已下載的 `qwen2.5:3b` 本地模型，同時驗證沒有模型時的追問路徑。
13. （實作時）停用鈕放在文件明細，不放在文件列：文件列本身是按鈕，裡面不能再放按鈕。
14. （實作時）`ai_answers` 和稽核紀錄一樣不放進去敏展示資料包（`demo_pack.EXCLUDED`），完整備份仍包含；因此多改了允許清單外的 `api/app/demo_pack.py` 一行。
15. （實作時）語意向量檢索仍沿用「驗收模式才開」的既有限制，所以 PostgreSQL 部署的正式文件是關鍵字檢索；要開向量另立項目。
