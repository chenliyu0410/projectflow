# N8N 第一批：通知外送與 AI 週報（實作計畫）

> **執行方式**：用 `/pf-next` 推進（CLAUDE.md），或依 WORKFLOW §14 手動逐 Task 執行。勾選框只供閱讀，進度記在 PROGRESS，不在本檔打勾。

**目標**：地端自架 n8n 負責排程與寄信；專流新增使用者 Email、服務帳號 token、outbox 事件、週報與每日摘要，Demo 全程單機離線寄進 Mailpit。

**架構**：n8n 只呼叫專流 `/integrations/*`（Bearer token）；所有信件先由專流寫成 `outbox_events`，n8n 每分鐘拉取寄出並回報結果。週報的資料整理、權限、AI（既有本地模型設定）與稽核都在專流。

**技術**：FastAPI／SQLAlchemy／Alembic、React＋Vitest、Docker Compose、n8n 社群版、Mailpit。

**規格**：[2026-11-02-n8n-batch1-design.md](../specs/2026-11-02-n8n-batch1-design.md)（含 D84、D85）。

## 全域限制

- 依 WORKFLOW §14：核心流程、migration、權限要有有效測試；pytest／Vitest 各記真實摘要與 exit code，沒實跑不能標通過。
- 分支：開工前先 `git branch -d feature/ocr-pipeline`（已併入 main；`-d` 遇未合併會拒絕），再 `git checkout -b feature/n8n-batch1`。不用 worktree，`git add` 明確路徑，ff-only 合併；push 要另外問使用者。
- migration 只新增，不改舊資料；舊帳號 `email` 為空、`email_notify` 為 true。
- 秘密不進 git：token、SMTP、`deploy/.env`。完整 token 只在建立回應出現一次，不寫稽核、不寫 log。
- 時區一律用固定 UTC+8（`timezone(timedelta(hours=8))`），不用 zoneinfo（Windows 沒有 tzdata）。
- 信件與畫面的使用者文字都要跳脫：信件 HTML 用 `html.escape`，React 用預設跳脫，不用 `dangerouslySetInnerHTML`。
- 介面文字用繁體中文。不使用 n8n 雲端 AI 節點；Docker 映像寫死版本號，不用 `latest`。
- 新依賴：不新增 Python／npm 依賴。

## 規格的兩處調整（AI 代決，理由見各 Task）

1. **一般 API 拒絕 token 回 401**，不是規格寫的 403。原因是一般 API 只認 cookie，Bearer 等於未登入；效果相同，都是拒絕。
2. **每日摘要改由 `POST /integrations/daily-digest` 寫成 outbox 事件**，不是 GET 讀取後由 n8n 直接寄。這樣才有去重（同人同日只一封）和失敗重試，n8n 流程也更單純。另外新增事件狀態 `skipped`：收件人停用、沒有 Email 或關閉通知時使用，不寄也不重試。

### Task 3：outbox 事件與通知接線

**檔案**：`outbox_service.py`、`notification_service.py`、`routes/integrations.py`、`test_integrations.py`

**產出**：
- `outbox_service.enqueue(db, organization_id, kind, recipient_id, subject, text, link, dedupe_key) -> OutboxEvent | None`
  - 同一組織的 `dedupe_key` 已存在就不新增，回 None
  - `body_html` 由 `text` 經 `html.escape` 並把換行轉成 `<br>` 產生，結尾加上專流連結
  - 連結基底取環境變數 `PF_PUBLIC_URL`，預設 `http://127.0.0.1:15173`
- `notification_service.emit()`：在 `db.add(Notification(...))` 之後、同一交易內呼叫 `enqueue`
  - `kind='notification'`，`subject='[專流] ' + message`
  - text 為「任務：<node.title>\n<message>」
  - link 為 `/projects/<project_id>?node=<node_id>`
  - `dedupe_key='notification:' + recipient_id + ':' + event_key`
- `GET /integrations/events?limit=20`（token）：
  - 依建立時間取 pending 事件
  - 收件人停用、沒有 Email 或 `email_notify=false` 時，改標 `skipped` 並略過

### Task 4：週報與每日摘要服務

**檔案**：`weekly_report_service.py`、`daily_digest_service.py`、`routes/weekly_reports.py`、`routes/integrations.py`、`test_weekly_reports.py`

**產出**：
- 常數 `TAIPEI = timezone(timedelta(hours=8))`；`week_start(today: date) -> date`（回傳當週一）
- `recipients(db, organization, project) -> list[User]`（D84）：
  - 專案負責人
  - 加上在此專案有負責任務（`Node.owner_user_id`）或協作（`NodeCollaborator`）、角色屬於 admin／project_owner／reviewer／readonly，而且帳號啟用中的人
  - 結果去重
- `explicit_confidential(organization_key, project_id, nodes) -> set[node_id]`（D85）：
  - 讀 `policy.load(key)['overrides']`；公司不在 `store.COMPANIES` 時視為沒有覆寫
  - 專案覆寫為 confidential：整個專案的任務都算
  - 節點或其任一上層覆寫為 confidential：該任務算
- `collect_facts(db, organization, project, recipient_users, now) -> (facts: dict, excluded: int)`：
  - 只看 `kind='task'` 且未刪除的節點
  - 列入條件：每位收件人 `can_view_node` 為 true，且不在 `explicit_confidential` 內；其他算進 excluded
  - facts 的鍵：`completed`、`pending_review`、`doing`、`due_next_week`、`overdue`、`blocked`、`silent_members`、`counts`，規則照規格 §4
  - 每個任務給短代號 `T1..Tn`（`ref`），附 `title`、`owner`、`due_date`，以及回報的 `result`、成果說明
  - `blocked` 用 `notification_service.states()` 判斷
  - `silent_members`：負責 doing 或逾期任務、本週沒有 TaskReport 也沒有 TaskNote 的人，只放顯示名稱
- `write_sections(organization_key, facts) -> (sections: dict, model_label: str)`：
  - 模型未啟用時，回原始整理的四段，`model_label='AI 未啟用'`
  - 啟用時用 `model.chat(config, SYSTEM, prompt, SCHEMA)`；SCHEMA 是 `{summary: str, highlights: [str], risks: [str], next: [str]}`
  - 提示要求引用任務時寫 `[Tn]`；某段出現 facts 沒有的 `[Tn]`，那一段改用原始整理
  - 任何例外（逾時、格式錯誤、`ValueError`）都退回原始整理
- `generate(db, actor: CurrentUser, project, now) -> WeeklyReport`：
  - 同專案同週已經是 sent 時回 409「本週週報已寄出」
  - 有 draft 就覆蓋；舊週的 draft 改成 unsent
  - 寫入資料後 enqueue 給負責人：`kind='weekly_draft'`，`dedupe_key='weekly_draft:'+report.id+':'+generated_at`
  - 稽核：`weekly_report.generate`（payload 有 project_id、model_label、excluded_count）；模型有啟用時，另寫 `ai.weekly_report`（本地處理、模型名稱）
- `confirm(db, current, report, sections) -> WeeklyReport`：
  - 只限專案負責人或 admin；draft 以外的狀態回 409
  - 重新計算收件人：停用或已經看不到列入任務的人移除，回傳 `removed`
  - 每位收件人 enqueue `kind='weekly_report'`，`dedupe_key='weekly_report:'+report.id+':'+user_id`
  - 信件內容：「AI 建議」標示、四段、數字表、任務清單
  - 稽核 `weekly_report.confirm`：確認者、收件人數，以及「修改了哪幾段」的段名，不放內文
- `daily_digest_service.enqueue_all(db, organization, today) -> int`：
  - 對每位啟用中的使用者，以他自己的 `CurrentUser` 檢查 `can_view_node`
  - 列出他負責的任務：昨天完成（`TaskReport.finished_on == 昨天` 且 approved）、今天到期、逾期、卡住
  - 四類都空就跳過
  - `dedupe_key='daily:'+user_id+':'+today`，回傳新增筆數
- 路由（session）：
  - `GET /projects/{id}/weekly-reports`：負責人和 admin 看全部；reviewer／readonly／project_owner 只看 sent；其他角色回 403
  - `POST /projects/{id}/weekly-reports/generate`：負責人、admin
  - `PATCH /weekly-reports/{id} {sections}`：只有 draft 可改，負責人、admin
  - `POST /weekly-reports/{id}/confirm`：負責人、admin
- 路由（token）：
  - `POST /integrations/weekly-reports/generate {project_ids?: [str]}`：沒有指定就跑該公司全部專案，回 `{generated, skipped_sent}`
  - `POST /integrations/daily-digest`：回 `{enqueued}`

- [ ] 寫測試（RED），用假模型 monkeypatch `model.settings`、`model.chat`：
  - 七個區塊各一個小情境
  - D84：member 不在收件人名單；reviewer 有負責任務時會被列入
  - D85：沒有覆寫時全部列入；節點覆寫 confidential 時，該任務和子任務都排除，`excluded_count` 正確
  - 模型未啟用時 `model_label='AI 未啟用'`，仍產生草稿
  - 假模型回傳清單外的 `[T99]`，該段改用原始整理
  - 已 sent 再產生回 409；舊週 draft 變成 unsent

  - 每日摘要：四類都空不 enqueue、同日重跑不重複、停用帳號不收
  - 稽核紀錄有 generate／confirm 和模型名稱
