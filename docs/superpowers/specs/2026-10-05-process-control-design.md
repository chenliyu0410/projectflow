# 流程控制（精簡版）設計

- 日期：2026-10-05
- 範圍：`projectflow-full-demo.html`、`tests/`
- 前置：W2 部門模型已完成，`db.v = 4`
- 來源：D31、D41，以及 `docs/reference/2026-10-05-w3-current-flow-sources.md`
- 狀態：草案，需人類看一次後定稿

## 1. 問題

目前 Demo 已有階段閘門、前置條件、任務狀態和模板，但展示情境仍停在寵物食品範例。使用者無法直接看到一個企業常見的新產品專流，也無法清楚感受到「上一階段關卡沒過，下一階段不能開始」這個流程控制。

D31 已把 W3 縮小成精簡版，只做兩件事：

1. 範本與示範專案。
2. 關卡硬性擋住後續階段。

D41 進一步決定不等原本的連接器甘特圖，改用現有兩份 Excel 先行。其中「產品企劃部-筆電新機種專流」有 G0-G6，作為主要展示流程；「行銷部-實體活動專流」只作輔助參考。

## 2. 目標

1. Demo 重置後有一個「筆電新機種」示範專案，依來源表建立階段、任務、部門與 G0-G6 關卡。
2. 模板庫有可辨識的「筆電新機種專流」範本，讓人知道這套流程可以重複套用。
3. 階段關卡未核准時，後續階段的任務不能切到進行中或完成。
4. 關卡通過後，被擋住的後續任務可正常開始；審核中心、階段列和任務操作提示都能看懂原因。

不在本次範圍：

- 不新增正式的流程設計器。
- 不新增或維護人員帳號。
- 不新增 W2 以外的部門管理能力。
- 不做範本指定關卡核准人、總經理角色、強制通過關卡、略過整個階段、完成報告必附交付物。
- 不處理外部 ODM 的帳號或外部協作權限。

## 3. 資料與種子內容

### 3.1 資料版本

W3 精簡版優先沿用現有資料結構，不升 `db.v`：

- `db.gates[phaseId]` 已可記錄階段關卡。
- `db.deps[]` 已可記錄任務前置。
- `db.templates[]` 已可保存任務樹、相對日期、協作部門與前置條件。
- `nodes[].dept` 和 `nodes[].depts` 已由 W2 提供。

只有在實作 plan 發現必須新增持久欄位時，才在 plan 裡明確改成 v5；否則維持 `db.v = 4`。

### 3.3 筆電新機種示範專案

`seed()` 新增一個專案「筆電新機種開發」，階段依來源表大項建立：

1. 市場洞察
2. 產品定義
3. 設計開發
4. EVT 工程驗證
5. DVT 設計驗證
6. PVT 生產驗證
7. 量產
8. 上市
9. 售後與停產

每個細項建立為任務。含 `（G0）` 到 `（G6）` 的任務同時作為該階段的關卡代表任務：

| 階段 | 關卡任務 | 關卡狀態 |
|---|---|---|
| 市場洞察 | 立案審查（G0） | approved |
| 產品定義 | 規格凍結（G1） | approved |
| 設計開發 | EVT 準備審查（G2） | pending |
| EVT 工程驗證 | EVT Exit（G3） | pending |
| DVT 設計驗證 | 設計凍結（G4） | pending |
| PVT 生產驗證 | 量產審查（G5） | pending |
| 量產 | 出貨許可（G6） | pending |

展示狀態：

- 前兩個階段已完成或接近完成，讓畫面一打開就看得到已核准關卡。
- 「設計開發」是目前階段。
- EVT 之後的任務預設 todo，且會被 G2 擋住。

### 3.4 範本庫

模板庫新增「筆電新機種專流」系統模板：

- scope：`system`
- category：`新產品`
- 內容採來源表的主要任務樹。
- 前置條件預設用階段順序串接：前一階段的關卡代表任務完成後，下一階段第一個任務才能開始。
- 模板保存相對日期，便於日後套用到其他專案或階段。

W3 不要求完整的一鍵建立新專案流程；只要 Demo 有示範專案，而且模板庫看得到這個流程即可。

## 4. 關卡阻擋規則

### 4.1 被擋範圍

對同一專案內的階段，若某階段 `A` 的 `db.gates[A.id].status` 不是 `approved` 或 `overridden`，則：

- `A` 後面所有階段的任務不能從 todo 切到 doing。
- `A` 後面所有階段的任務不能直接切到 done。
- 後續階段的階段節點本身不強制阻擋瀏覽；使用者仍可點進去看有哪些任務。

當有多個未過關卡時，提示顯示最前面那個未過關卡。

### 4.2 不被擋的操作

- 可以瀏覽後續階段與任務。
- 可以編輯後續階段任務的基本資料、負責部門、負責人與時程，只要原本權限允許。
- 可以新增筆記、文件和前置條件，只要原本權限允許。
- 可以核准目前階段的關卡。

這樣 Demo 能展示規劃未來工作，但不能假裝流程已經開跑。

### 4.3 提示文字

任務被擋時，沿用既有前置阻擋的體驗，顯示：

`階段關卡未通過：{階段名稱}／{關卡條件}`

看板卡片與任務頁可沿用現有「等待前置」標籤，不新增新視覺系統。需要時標籤 title 裡列出關卡原因。

### 4.4 審核中心

審核中心目前已有「待核准的階段閘門」。W3 只要求：

- 筆電新機種專案的 pending gate 會出現在此區。
- 核准 G2 後，EVT 階段任務不再被 G2 擋住。
- 退回或未核准時，後續階段仍被擋住。

## 5. 權限

- 關卡核准沿用現有 `can('gate', phase)`。
- 關卡覆寫沿用現有 `can('override', phase)`，但 W3 不新增「強制通過關卡」功能；現有覆寫流程維持。
- 任務開始與完成仍先檢查原本的任務權限與前置條件，再加上階段關卡阻擋。
- 所有資料變更照 AGENTS 規則：包在既有 `commit(label, fn)` 裡，並呼叫 `log(nodeId, action, text)` 寫稽核紀錄。

## 6. 畫面

### 6.1 專案列表與階段列

筆電新機種專案出現在既有專案列表中，不新增頁面。

階段列沿用目前樣式：

- approved gate 顯示已核准。
- pending gate 顯示未過。
- 目前階段維持既有「目前階段」提示。

### 6.2 看板與任務頁

被階段關卡擋住的後續任務：

- 看板卡片顯示等待提示。
- 嘗試切到進行中或完成時，開啟既有 blocked dialog 或 toast，說明是哪個階段關卡未通過。
- 375px 寬度不能出現水平捲動。

### 6.3 模板庫

模板庫顯示「筆電新機種專流」，包含任務數、前置數與約略天數。文字使用繁體中文。

## 7. 測試

在 `tests/records.test.js` 新增瀏覽器測試：

1. 種子資料有「筆電新機種開發」專案，包含 9 個階段與 G0-G6 gate。
2. 筆電新機種專案的任務帶入 W2 部門 id；ODM 不會變成不存在的部門 id。
3. 模板庫有「筆電新機種專流」，且保留任務樹和前置條件。
4. G2 pending 時，EVT 階段的任務不能切到進行中，錯誤訊息包含「階段關卡未通過」與「設計開發」。
5. 核准 G2 後，同一個 EVT 任務可以切到進行中。
6. 既有硬性前置仍然有效：即使關卡已過，任務自己的硬性前置未滿足時仍不能開始。
7. 審核中心列出筆電新機種的待核准 gate。
8. 375px 下看板與任務頁沒有水平捲動。

整體測試仍用 `tests/records.html`，記錄 RED 與 GREEN 的 `#sum` 原文。
