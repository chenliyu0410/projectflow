# P2b：回報、審核與協作設計草案

日期：2026-10-08。程式基準：`c0284f6`。依據：[路線圖](../../formal-feature-roadmap.md)、README F6／F11、[PROGRESS D58／D59](../../PROGRESS.md)。

**狀態：G1討論草案，未定稿、不可據此實作。** 人類已指示接續P2b；下列推薦規則尚待確認。本文件先明確列出第一個需要定案的流程，以及後續設計工作，不把Demo規則自動當成正式版授權。

## 1. 目標與範圍

讓使用者在既有P2a任務工作區留下工作成果、送審、退回重送、確認完成，並透過筆記、附件與協作角色完成多人工作。

對應B1–B6：回報審核服務、回報介面、筆記與協作、主機附件、審核中心與稽核、隔離整合交付。保留既有專案、任務日期、回報、稽核及試用資料；Demo與其測試不改。

不把P2c時程／模板管理／一般相依排程、P2d AI／ERP、LAN／TLS或人類試用簽核納入本次完成宣告。跳過／覆寫申請是否納入P2b須另定案，不能默默沿用Demo子樹操作。

## 2. 已核對的現況

| 項目 | 現有程式行為 | P2b設計影響 |
|---|---|---|
| `POST /nodes/{id}/reports` | 驗can_work_node，新增submitted回報與report.submit稽核；不改Node.status | 不能只加審核按鈕便宣稱已有狀態流程 |

| 回報查詢與審核 | 尚無清單／確認／退回端點 | 需新API、UI與競態保護，不能只改現有POST |
| 稽核查詢 | 限公司、最新50筆，回傳actor_username與原payload | 必須另核定節點可見範圍、欄位投影與分頁；不可把現有原payload直接展示給所有成員 |
| 協作 | 無Node協作資料；member可見本人負責的節點，我的任務只列本人負責 | 新增協作可見性時须同步詳情、總覽、搜尋、本人入口及附件授權 |
| 附件 | 無正式附件模型、服務或檔案volume | 需獨立持久化、每次下載授權及DB／檔案失敗處理；不能寫到容器暫存層 |

## 3. 第一個決策：完成是否必須經過審核（D59）

### A：回報驅動完成（推薦）

1. 執行者填寫成果並送出，任務進入review；此回報內容鎖定。
2. 有審核權限者確認後進入done；退回必填意見，任務回doing。
3. 退回後重送建立新版本，保留前次回報與退回紀錄，不能覆寫歷史。
4. 同一任務同時至多一筆待審版本；兩人並行送出或審核只能成功一次，另一方收到可理解的衝突提示。
5. 一般狀態選單及直接呼叫status API都不能繞過送審進入review／done；已有待審回報時不得以另一條狀態更新使回報與任務脫節。
6. 回報、任務狀態與稽核在同一交易提交；失敗時不得留下部分狀態。沿P2a實體祖先Gate檢查，不依可見樹判定。

代價：改變P2a直接標記完成的操作習慣，需要調整既有API／UI回歸測試；但能讓「確認完成」具有實際約束力。管理者是否可自送自核、完成後重新開啟與跳過規則，於下一步明確定案，不能從此推薦推定。

### B：回報審核與任務狀態分開

新增回報確認／退回及歷史，但保留可操作者直接改done；回報審核結果不強制控制任務狀態。

代價：相容現有操作，但任務可在回報尚未核准時顯示完成。UI須明確區分「任務狀態」與「回報審核結果」，不能宣稱完成必須審核。

### 既有資料的必要相容條件（兩方案皆遵守）

- 已有done任務不回退，舊回報的ID、文字、提交人與時間及既有稽核不改寫。
- 歷史submitted回報未必對應review，且一個任務可能多筆；migration不能直接把它們全當新待審流程，亦不能先加唯一約束而使升級失敗。
- 方案A定案後須提供歷史記錄的識別／顯示規則與明確啟用界線，避免舊回報被新審核端點誤操作。具體schema於完整規格與plan列明。
- 不做自動回溯核准、不刪除重複歷史、不重設seed。

## 4. 後續依序定案事項

此表為設計議程，不是已批准的需求刪減或實作計畫。

| 主題 | 下一步要確認的內容 |
|---|---|
| 審核授權與鎖定 | admin、實際專案擁有者、reviewer、部門主管的權限範圍；是否允許自送自核；done後重新開啟；phase／有子任務task是否回報 |
| 表單與歷史 | 結果三選項、成果說明、實際完成日；自訂欄位與快照是否本期交付；舊任意result的展示 |

| 協作 | 管理者設定人員／部門；授予哪些讀取與筆記能力；不默認授予完成／改派權限；子樹繼承及撤銷後搜尋／附件可見性 |
| 附件 | README F11單檔10 MB、SHA-256、軟刪除及回報附件保護；類型／總容量、上傳失敗、孤立檔案與備份恢復 |
| 審核中心／稽核 | 待審回報與既有Gate的各自授權；可見範圍過濾後分頁；安全payload投影；跳過／覆寫申請的本期邊界 |

## 5. 計畫拆分準備

規則定案後才產出G2可執行plan：每個Task列明允許檔案、介面、RED／GREEN命令、commit與兩位獨立審查。預期依序拆為：

1. 保留資料migration、共用授權與回報／審核狀態交易。
2. 回報歷史、送審／退回／確認介面。
3. 協作資料與全讀取路徑的可見性、筆記服務與介面。
4. 主機附件儲存、上傳／下載／軟刪除及回報／筆記關聯。
5. 審核中心與安全稽核查詢。
6. 兩公司／角色／並行請求、真PostgreSQL升級、DB與附件重啟持久化、1280／375、文件與交付。

具體Task數量依已確認規則調整，不用此順序繞過G1或G2。關鍵端對端旅程先取得功能RED，再實作，不在功能完成後破壞程式製造RED。

## 6. 驗收底線

- API是唯一權限來源；readonly、其他公司、不可見節點與附件均有拒絕及無副作用測試。
- 審核版本、筆記、附件和稽核不洩漏隱藏任務；撤銷協作後每次讀取重新授權。
- 回報與審核防重送、防舊回應覆蓋，401清草稿，寫入成功而重讀失敗只能重試讀取。
- 測試只用隔離Compose／marker，寫入前拒絕15173；另建migration測試DB，保留現有DB、檔案及.env。
- 合併前後完整API／Vitest／build／Playwright與實際桌面／手機驗收；保留舊row與附件的升級／重啟證據。
- README、正式指南、試用清單及PROGRESS隨工程交付更新；人類試用簽核仍由人類完成。

本輪未跑P2b產品測試、未實作migration或部署；P2a已通過的測試數僅為後續G3需重跑核對的歷史基準。
