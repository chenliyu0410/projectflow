# 部門模型 設計

- 日期：2026-10-01
- 範圍：`projectflow-full-demo.html`（單檔 Demo）、`tests/`
- 背景：對照 10 部門流程甘特圖（連接器新產品，6 階段、每件工作由部門負責），把「部門」變成正式資料。
- 拆分：本份是兩份 spec 的第一份。
  - 第一份「部門模型」（本文件）：可設定的部門與主管、任務的負責部門、未指派可見性、時間軸收合與部門篩選。資料升到 v4。
  - 第二份「流程控制」（之後另寫）：關卡硬性擋住後續階段、範本指定關卡核准人、總經理角色、強制通過關卡與略過整個階段、完成報告必附交付物、連接器範本與示範專案。資料升到 v5。

## 1. 問題

- 部門寫死在 `DEPTS` 常數（7 個），與實際的 10 個部門不同；資訊室的「資訊」不在清單裡。
- 任務只能指派給「人」，負責部門是從負責人推出來的。實務上範本建專案時只知道哪個部門做，還不知道是誰。
- 一般成員幾乎看得到、改得到所有任務，不符合「只有相關的人看得到」。
- 時間軸一次攤開所有工作，無法像流程甘特圖一樣先看階段、再依部門看細項。

## 2. 目標

1. 部門可由系統管理員維護，每個部門可設一位主管。
2. 任務有必填的負責部門，負責人選填；未指派時由部門主管指派。
3. 任務只有相關的人看得到、能操作。
4. 時間軸預設收合成階段，可依負責部門篩選展開的工作。

不在本次範圍：關卡、核准人、交付物、連接器範本（第二份 spec）；應收帳款（「開發票、請款」維持一般任務）；人員帳號的新增與編輯（`USERS` 仍為常數）。

### 3.3 節點

- `dept`：負責部門 id。`type === 'task'` 必填；專案、階段為 `null`。
- `owner`：任務的負責人改為選填，`null` 表示「未指派」。專案、階段的 `owner` 不變。
- `depts[]`：協作部門，改存部門 id。
- `addNode()` 接受 `dept`；建立任務時若沒給 `dept`，預設為父任務的 `dept`，再沒有則為建立者的部門。

### 3.4 v3 → v4 升級（`upgrade()`）

1. 加上 `db.departments`（預設 10 個）。
2. 舊部門名稱對應：研發→d-rd、製程→d-pe、品保→d-qa、法規→d-qa、採購→d-pur、生產→d-mfg、行銷→d-sales、資訊→d-it。套用到每個節點的 `depts[]`（轉換後去重）。
3. 每個任務的 `dept` 設為負責人所屬部門（`USERS[owner].dept`）；負責人不在 `USERS` 時設為 d-rd。負責人保留，所以既有任務都是已指派。
4. 模板節點（`db.templates[].nodes`）的 `dp` 套用同一份對應，並補上 `dept`（有 `who` 取其部門，否則取模板的第一個 `dp`，再沒有則 d-rd）。
5. `d.v = 4; o.v = 4`。`load()` 接受 v2、v3、v4；`save()` 寫入 v4。升級依序執行（v2→v3→v4）。

### 3.5 種子資料

- `seed()` 直接產生 v4 結構。
- 新增 3 件未指派任務（`owner: null`），用來展示可見性：
  - 研發部 1 件（力瑜可見）
  - 品保部 1 件（陳主管可見，小安不可見）
  - 製程部 1 件（製程未設主管，只有專案負責人與系統管理員可見）

### 3.6 部門的新增、修改、刪除

- 新增：名稱必填、不可與現有部門重複；id 用 `newId('d-')`。
- 修改：可改名稱與主管；主管只能選該部門的成員（`deptMembers`）或「未設主管」。
- 刪除：只要有任何任務 `dept`、任務或模板的協作部門、使用者屬於該部門，就拒絕並以 toast 提示「部門還有 N 件任務、M 位人員，請先移轉」。
- 以上操作都走 `commit()`（可復原）並寫入稽核紀錄。

## 4. 可見性與權限

### 4.1 誰看得到任務（取代現有 `visible()`、`related()`、`shown()`）

`directSee(n, u)`：使用者 `u` 是否直接看得到任務 `n`。

- 未指派（`n.owner === null`）：
  - `u` 是 `n.dept` 的主管。
- 已指派：
  - `u` 是負責人；或
  - `u` 在協作人員 `n.collabs`；或
  - `u` 是 `n.dept` 的主管；或
  - `u` 是任一協作部門 `n.depts` 的主管；或
  - `u` 是審核人（`role === 'reviewer'`），且 `n` 所在階段在他的 `scope` 內。

`seeTask(n, u)`：

- `u.role` 是 `admin`、`owner`、`readonly` → 看得到全部。
- 否則看得到，條件是 `directSee(n, u)`，或任一**上層任務**符合 `directSee`（負責上層任務的人看得到它的子任務），或任一**下層任務**符合 `directSee`（只為顯示路徑）。

專案與階段：使用者看得到專案底下任一任務時，就看得到這個專案和它的**所有階段列**（階段是結構，任務才過濾）。`admin`、`owner`、`readonly` 看得到全部專案。

- 移除 `ui.showAll`、`fullViewAllowed()` 與工具列的「顯示全部任務」核取方塊，以及 collab 專用的「只顯示指派給你的任務」標籤。
- 切換身分（`meSel`）後若目前節點看不到，沿用現有的跳回第一個看得到的專案。

### 4.2 誰能操作任務

「操作」指：改狀態、改進度、送完成報告。由新的 `canWork(n)` 判斷：

- 系統管理員、專案負責人（`role === 'owner'`）、`n.dept` 的主管：可以。
- 負責人本人：可以（已指派時）。
- 其他人（含協作人員、協作部門主管、同部門成員）：不可以。

協作人員與協作部門主管照舊可以新增筆記（F11）。F11 的 `canReport(n)` 改為呼叫 `canWork(n)`。

### 4.3 指派與改部門

- 指派負責人（`can('assign', n)`）：系統管理員、專案負責人、`n.dept` 的主管。負責人只能選 `deptMembers(n.dept)`。
- 改負責部門（`can('dept', n)`）：系統管理員、專案負責人。改部門時若原負責人不在新部門，`owner` 設為 `null`。

### 4.4 現有 `can()` 的調整

- `'view'`：改用 `seeTask`。
- `'edit'`（改標題、說明等）：系統管理員、專案負責人、`n.dept` 主管、負責人本人。
- `'schedule'`：member 的「自己的任務」條件改為「負責人本人或 `n.dept` 主管」；owner、reviewer 不變。
- 其餘動作（`delete`、`deps`、`gate`、`override`、`members` 等）不變。
- `viewPeople()` 的權限矩陣表格同步更新文字，並加一列「指派負責人：部門主管」。

## 5. 畫面

### 5.1 部門設定（「人員」分頁）

在 `viewPeople()` 的成員面板之後加「部門」面板：

- 表格欄位：部門名稱、主管、成員數、任務數。
- 主管為空時顯示 `<span class="tag warn">未設主管</span>`，滑鼠提示「這個部門的未指派工作只有專案負責人看得到」。
- 只有系統管理員看得到「＋ 新增部門」、每列的「編輯」「刪除」按鈕；其他身分只讀。
- 新增和編輯共用一個對話框（名稱、主管下拉）。

### 5.2 任務對話框

- 新增「負責部門」下拉（必填），沒有 `can('dept', n)` 權限時停用。
- 「負責人」下拉：第一項「未指派」，其後列出 `deptMembers(所選部門)`。沒有 `can('assign', n)` 時停用。切換部門時，若原負責人不在新部門就重設為「未指派」。
- 「協作部門」核取清單改讀 `db.departments`，儲存部門 id。
- AI 建議協作部門的流程（現有）改為輸出部門 id。

### 5.3 看板、任務頁、我的任務

- 未指派任務的卡片與任務頁標題：`<span class="tag warn">未指派・{部門}</span>`，負責人欄位顯示「—」。
- 已指派的卡片照舊顯示負責人頭像，旁邊加小字部門名稱。
- 「我的任務」：
  - 部門主管多一組「待我指派」，列出自己部門 `owner === null` 的任務（依截止日排序），每項有「指派」按鈕，開啟任務對話框。
  - 原本「部門被指派的任務」群組移除（同部門成員已看不到）。
- 總覽的部門工作量面板改用 `db.departments`，依負責部門統計。

### 5.4 時間軸（`viewTimeline`）

- 有階段的專案：
  - 預設每個階段收合，只顯示階段列。點階段列的名稱可展開或收合，可同時展開多個。
  - 階段列上顯示「▸ N 件」或「▾ N 件」（N 為使用者看得到、且符合目前篩選的任務數）。
- 部門篩選列：放在時間軸工具列下方，按鈕依序為「全部」與 `db.departments` 各部門，每個按鈕顯示件數（使用者看得到的任務中，負責部門符合的件數）。件數為 0 的部門按鈕仍顯示但淡化。
  - 篩選只看負責部門 `n.dept`，不看協作部門。
  - 篩選只影響工作列；階段列永遠完整顯示。
  - 被篩掉的任務，其依賴箭頭不畫；子任務符合篩選時，上層任務以淡色顯示作為路徑。
  - 要徑計算不受篩選影響，只是顯示時隱藏。
- 沒有階段的專案：不收合，篩選直接套用在所有工作上。
- 展開狀態存在 `ui.tlOpen`（`{ [phaseId]: true }`），篩選存在 `ui.tlDept`（`'all'` 或部門 id）。兩者不寫入 `db`、不進入復原紀錄、切換專案時保留。
- 拖拉改期、連動平移、復原等現有操作在展開的工作上照舊。

### 5.5 範本

- 模板節點加 `dept`（必填）。模板編輯畫面每列加「負責部門」下拉。
- `applyTemplate()`：
  - 建立的任務帶 `dept: x.dept`。
  - `opt.owners` 為真且 `x.who` 屬於 `x.dept` 時才帶入負責人；否則 `owner: null`（未指派）。原本預設 `ui.me` 的行為移除。
- `PHASE_TEMPLATE` 的每件任務改成 `[標題, 部門 id]`，由「依範本建立專案」流程（約 :2691）帶入。寵物食品範本的部門依 3.4 的對應表設定。

## 6. 錯誤處理

- 儲存任務時 `dept` 為空 → toast「請選擇負責部門」，不儲存。
- 負責人不在所選部門（例如資料被手動改過）→ 儲存時清為未指派，toast 提示。
- `deptName()` 找不到部門時顯示「—」，不拋錯。
- 升級時遇到不在對應表的部門名稱 → 對應到 d-rd，並在稽核紀錄寫一筆「部門 X 已併入研發」。

## 7. 測試

新增 `tests/departments.test.js`，由 `tests/records.html` 在 `records.test.js` 之後載入並合併結果（頁面標題改為「Demo 測試」）。沿用相同的 `T`、`eq`、`ok`、`as` 工具。

1. 種子資料：`db.v === 4`；10 個部門；每個任務都有 `dept`；3 件未指派任務存在。
2. 升級：建立 v3 資料（部門為名稱字串），`upgrade()` 後部門 id 對應正確（法規→d-qa、生產→d-mfg、行銷→d-sales）、`depts[]` 去重、任務 `dept` 等於負責人部門、模板節點有 `dept`。
3. 可見性矩陣：以 yu、ming、an、hua、chen、lin、it 七個身分，對「未指派品保任務」「已指派給 ming 的製程任務」「lin 為協作人員的任務」「協作部門含採購的任務」各驗證 `seeTask` 結果。
4. 未指派、無主管部門（製程）的任務：只有 yu 與 it 看得到。
5. 路徑：負責子任務的人看得到上層任務；負責上層任務的人看得到子任務。
6. 操作：`canWork` 對負責人、部門主管、同部門成員、協作人員的結果。
7. 指派：主管可以指派，負責人只能選部門成員；改部門會清空不屬於新部門的負責人。
8. 部門刪除：有任務或人員時拒絕；空部門可刪；可復原。
9. 時間軸篩選：設定 `ui.tlDept = 'd-qa'` 後，渲染結果的階段列數不變，工作列只有品保負責的任務。
10. `applyTemplate()`：未勾負責人時任務皆為未指派且帶 `dept`。

現有 `records.test.js` 中依賴 `DEPTS`、部門名稱字串或 `showAll` 的斷言，改成新的結構，並在 `db.v` 的斷言改為 4。
