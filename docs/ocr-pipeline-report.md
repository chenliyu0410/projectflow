# OCR-PIPE 文件解析模組：成果報告

2026-10-28，一日展示版。本文數字全部取自實測：Windows 本機的 `output/ocr-report/result.json`，以及斷網 Linux 容器的同一份輸出。樣本是 `deploy/ocr-eval/make_samples.py` 產生的虛構資料（毛研食品）。

## 架構

上傳檔案 → 格式判斷（副檔名、有無文字層）→ 三條路：文字層 PDF 用 pypdf 擷取；掃描檔先前處理，再交給 RapidOCR 繁中模型；Word／Excel 用既有的安全解析器 → 清理與正規化 → 統一輸出（文字＋檔名、頁碼）→ 切成 RAG 段落。

| 元件 | 檔案 |
|---|---|
| 統一入口、逐頁分路、計時 | `api/app/ai/ingest.py` |
| 前處理、標點正規化 | `api/app/ai/ocr.py` |
| 清理與正規化 | `api/app/ai/cleanup.py` |
| 1−CER、分路統計 | `api/app/ai/ocr_metrics.py` |
| 展示指令與 HTML 報告 | `deploy/ocr_pipeline.py` |

## 實測結果

| 樣本 | 逐頁路徑 | 1−CER |
|---|---|---|
| 報到公告-清晰.png | OCR | 92.4% |
| 報到公告-模糊.png（灰、模糊、傾斜、縮小） | OCR | 89.9% |
| 設備借用簽收單-掃描2頁.pdf | OCR、OCR | 92.8% |
| 混合文件-文字頁加掃描頁.pdf | 文字層、OCR | — |
| 文字層PDF、會議紀錄.docx、採購清單.xlsx | 文字層／Office | — |

有標註的三份樣本，平均 1−CER 為 **91.7%**。7 個檔案、9 頁，共產生 9 個 RAG 段落。

| 路徑 | 每頁秒數（Windows） | 每頁秒數（Linux 容器） |
|---|---|---|
| 掃描→OCR | 0.683 | 0.422 |
| 文字層 PDF | 0.009 | 0.009 |
| Word／Excel | 0.002 | 0.002 |

## 報告亮點

1. **逐頁分路，而不是逐檔分路**：同一份 PDF 裡，有文字層的頁面直接用 pypdf 擷取，只有掃描頁才跑 OCR。OCR 每頁約 0.68 秒，文字層每頁只要 0.009 秒，相差約 **75 倍**。這樣做既省時間，也不會讓 OCR 誤改原本正確的文字。混合文件的報告顯示它同時走了兩條路。
2. **繁體中文專用模型**：預設的簡體模型會把繁體字認成簡體或漏字，所以改用 RapidAI 官方的繁中辨識模型，並以 SHA-256 鎖定模型檔（`deploy/ocr-models.sha256`）。
3. **前處理有量化證據**：前處理包含灰階、自動對比、小圖放大。同一張模糊圖關閉前處理時 1−CER 只有 **59.5%**，開啟後是 **89.9%**，**提升 30.4 個百分點**。清晰圖本身夠大，前處理不會放大它，所以開關前後結果相同。這說明前處理只在需要時才發揮作用。
4. **用數據找出錯誤，再修正**：第一次實測發現，模型會把行尾的全形「。」辨識成「·」。補上一條正規化規則後，清晰圖 89.9%→92.4%、模糊圖 87.3%→89.9%、掃描 PDF 91.0%→92.8%。
5. **寧缺勿錯的信心門檻**：信心低於 0.5 的行直接丟掉，整份平均低於 0.6 就不採用；OCR 文字會標註「可能有錯字」。例如測試中的「雜訊」行（信心 0.2）就沒有進入輸出。對 RAG 來說，錯的資料比沒有資料更危險。
6. **清理讓 RAG 更準**：去掉重複的頁首「毛研食品 內部文件」和「第 N 頁」，避免每個段落都混進同樣的雜訊而干擾檢索；接回被行寬切斷的句子；Excel 每一列轉成「品名：鮪魚罐；數量：3；單價：45」，讓模型看得懂每一欄的意思。
7. **統一輸出＋頁碼 metadata**：三條路最後都輸出同一種結構，段落不跨頁，每段都帶 `filename`、`page`、`route`。AI 回答時，引用可以精準回溯到「哪個檔案第幾頁」。
8. **可量測、可重現**：用 1−CER 和每頁秒數兩個指標，一行指令就能產生 HTML 報告。樣本和標註都在 repo 裡，任何人都能重跑出同樣的數字；單元測試 18 項涵蓋分路、清理、指標和開關。
9. **可隨處地端部署，有斷網證據**：OCR 全部在本機 CPU 上執行。同一套程式在 Windows 本機和 Linux 容器（Python 3.13.18、x86_64）都能跑；在完全斷網（`--network none`，實測連不到 pypi.org）的容器裡，模型雜湊核對通過，跑完整條管線的 1−CER **和 Windows 一字不差**。模型以唯讀 volume 掛載；映像檔可以用 `docker save` 帶進隔離網路；沒有模型時 OCR 自動關閉，部署不會因此失敗。

## 實作中依建議做法處理的問題

- **Excel 不加 openpyxl**：沿用既有解析器，它有防壓縮炸彈和 XXE 的保護。
- **展示入口用指令產生 HTML 報告，不做網頁上傳**：避免在一天內處理登入和權限。
- **標註檔被當成輸入**：`.gt.txt` 的副檔名是 `.txt`，所以在展示指令中排除。
- **Docker 裡 pip 拒絕安裝 rapidocr**：套件宣告只支援 Python 3.13 以下，但實測在 3.13 可以執行，所以安裝 OCR 鎖版時加上 `--ignore-requires-python`。

## 限制（誠實列出）

- 樣本是用字型畫出來的合成掃描圖，不是真實的手機翻拍或影印件；真實文件的正確率可能較低。
- 剩下的錯誤主要是形近字，例如「線→綜」、「於→放」、「並→立」、「洽→治」、「台→合」，這是模型的限制。三份樣本都沒有達到原本預期的 95%。
- 只測過單機 CPU；沒有處理手寫字、多欄版面和傾斜校正。
- 尚未接進正式文件索引（`formal_index`）和網頁上傳，這是下一步。

## Demo 講稿（3 分鐘）

1. 秀架構圖，說明「逐頁判斷、三條路、統一輸出」。
2. 執行 `api/.venv/Scripts/python.exe deploy/ocr_pipeline.py deploy/ocr-eval/samples --models ../ocr-models --compare-preprocess`，終端機會逐檔印出路徑。
3. 打開 `output/ocr-report/report.html`：
   - 混合文件同一份 PDF 走了兩條路。
   - 展開掃描 2 頁 PDF：頁首尾不見了，斷行接回來了。
   - Excel 變成「欄位：值」。
4. 分路秒數表：OCR 比文字層慢約 75 倍，說明為什麼要逐頁判斷。
5. 前處理 A/B 表：模糊圖 59.5%→89.9%。
6. 展開 RAG 段落，指出每段都帶檔名和頁碼。
7. （加分）秀斷網容器的輸出：模型雜湊 OK、連不到網路、結果和 Windows 一致。
